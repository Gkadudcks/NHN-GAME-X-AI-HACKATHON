## 이번 기록에서 확정한 것

1. DAY 5의 PT는 이미 적용을 마친 개선 결과 보고가 아니라, 4일 동안 조사한 신규 유저 첫 전투 도달률 개선안을 제안하는 발표다. 개선안은 아직 라이브 서비스에 적용되지 않았다.
2. DAY 5의 사고는 발표 자료 본문이 다시 바뀌는 방식이 아니다.
3. 발표 자료에는 가장 최근 자료에서 확인된 현재 7일 차 잔존율 `18.4%`가 표시된다. 이 수치는 개선 후 성과가 아니라 현재 상태를 설명하는 확인값이다.
4. 평가위원이 열어 본 제출용 검증 자료에는 2024년 당시 수치 `12.7%`가 표시된다.
4. 두 수치의 불일치는 평가위원의 질문으로 처음 드러난다.
5. DAY 4 제출 직후에는 발표 자료와 근거 자료 모두 `18.4%`였으며, 도윤과 하린은 이를 확인하고 기록했다.
6. 실제 이전 기능 재실행 요청자는 강민재다.
7. 서하린은 자동 연결 기능의 등록 담당자일 뿐, 이번 재실행 요청자가 아니다.
8. 나나봇은 연결된 자료를 규칙대로 처리한 실행 기능이며 독립적으로 사건을 일으킨 주체가 아니다.
9. 민재의 핵심 잘못은 영향 범위를 확인하지 않고 이전 기능 재실행을 요청한 것과, 이상 징후 이후에도 요청 사실을 숨긴 것이다.
10. 최종 추리는 기존 단서 탭과 마인드맵에서 관련 DAY와 단서를 제시하는 `오류 검증` 미니게임으로 구성한다.
11. 오류 검증 다섯 단계는 실수 기회 5회를 공유하며, 결과창에서 `완전 검증`, `부분 검증`, `검증 실패`를 확인해야 종료된다.
12. 검증에 실패해도 담당자가 남은 경로를 정리해 스토리는 계속되며, 오류 검증 등급·근거 자료 복구·신뢰도·호감도로 세 엔딩을 판정한다.

   - 선택지: `두 자료가 같은 대상과 기간을 사용하는지 질문의 전제부터 확인하겠습니다.`

## 10:00 · 신규 유저 첫 전투 도달률 개선안 발표

도윤은 라이브 서비스 중인 RPG의 신규 유저 이탈 문제를 진단하고 개선안을 제안한다. 발표 논리는 `현재 신규 유저 퍼널 확인 → 첫 전투 이전 이탈 문제 → DAY 2에서 선택한 조사로 원인 구체화 → DAY 1에서 선택한 방향으로 해결안 제안 → 일부 신규 유저 대상 검증 계획` 순서로 진행된다. 핵심 수치는 이탈률 `31.9%`와 현재 `7일 차 잔존율 18.4%`이며, `18.4%`는 개선 성과가 아니라 현재 상태를 설명하는 확인값으로만 언급한다. 발표 본문은 정상이며, 하린과 박태식도 별다른 이상을 발견하지 못한다.

DAY 2에서 선택한 조사(`competitor`/`reviews`/`journey`)만 원인 근거로, DAY 1에서 선택한 방향(`shorten_tutorial`/`contextual_guide`/`ai_help`)만 구체적인 개선안으로 발표에 등장한다. 09:45에 선택한 `presentationFocus`에 따라 도입 문장과 평가위원의 첫 반응이 달라진다. 선택은 수치 불일치 사건의 발생 여부를 바꾸지 않는다.

발표를 마치면 평가위원과 정상적인 질의응답을 한 번 거친다(10:12 질문 → 10:13 답변 → 10:14 확인). 이 정상 질의응답이 끝난 뒤에야 10:16 평가위원이 공식 근거 자료를 열면서 연결된 자료가 다시 읽힌다.

## 10:18 · 평가위원의 질문

평가위원이 제출용 검증 자료를 열어 수치 차이를 발견한다.

- **한도윤**

- **박태식**
  - 도윤 씨, 지금 확인한 기록으로 설명할 수 있겠어?
- **서하린**
  - 원인을 먼저 단정하지 말고, 어느 수치가 검증됐는지부터 보여 줘요.

09:12 선택은 이 장면의 첫 대응을 다음처럼 바꾼다.

- `defend_evidence`: 도윤이 정상 수치가 `18.4%`라고 먼저 밝히고 DAY 2 교차 검증 기록을 제시한다.
- `clarify_scope`: 두 자료의 대상과 기간이 같은지 먼저 묻는다. 동일하다는 답을 받은 뒤 정상 근거를 제시한다.
- `coordinate_harin`: 하린에게 정상 원본을 열어 달라고 요청하고, 도윤이 직접 분석 기준과 차이를 설명한다.
- `speculate_cause`: 자동화 오류를 추측할지, 하린의 조언을 떠올리고 증거부터 제시할지 한 번 더 선택한다.

## 근거 자료 복구

정상 원본과 교차 검증 기록을 사용해 제출용 근거 자료를 네 단계로 복구한다.

```text
1. 자동 갱신 일시 중지
2. 현재 분석 원본 18.4% 선택
3. 신규 가입 사용자의 7일 차 잔존율 기준 확인
4. 고정 원본 연결 + 자동 갱신 끔
```

현재 선택 단계는 다음과 같다.

- `recoveryRefresh`: 자동 갱신 일시 중지 / 자동 갱신 유지
- `recoverySource`: 현재 분석 원본 `18.4%` / 과거 보관 자료 `12.7%` / 출처 불명 미리보기
- `recoveryBasis`: 신규 가입 사용자 / 가장 최근 자료 / 가입 후 7일
- `recoveryBinding`: 고정 원본 연결 + 자동 갱신 끔 / 자동 연결 유지

단순히 숫자를 다시 입력하는 복구가 아니다. 현재 원본과 분석 기준을 확인하고 고정 연결을 선택해 같은 사고가 반복되지 않게 한다. 현재 구현에는 복구 제한 시간이 없다.

## 수치 정정 결과 보고 및 질의응답 최종 답변

이 구간은 "발표 재개"가 아니다. 본 발표는 이미 끝났으므로, 복구 결과를 보고하고 정상 질의응답에서 다루지 못한 부분을 정리하는 질의응답 최종 답변으로 진행한다.

- **한도윤**
  - 확인 결과, 이번 발표의 현재 기준값은 7일 차 잔존율 18.4%입니다. 제출 근거에는 2024년 당시 수치인 12.7%가 잘못 연결돼 있었습니다. 정상 원본으로 근거 자료를 복구했고, 산정 기준과 제출 이후 변경 경로도 함께 남겼습니다.
  - 그리고 18.4%는 이번 개선안으로 얻은 성과가 아니라 현재 상태를 설명하는 확인값입니다. 제안한 개선안의 효과는 아직 검증 전입니다. 일부 신규 유저를 대상으로 첫 전투 도달률 5%포인트 개선을 확인하고, 7일 차 잔존율과 사용자 반응이 함께 좋아질 때만 전체 적용을 제안하겠습니다.
- **평가위원**
  - 현재 수치와 2024년 자료의 연결 오류, 그리고 제안의 검증 범위를 확인했습니다. 개선안의 타당성과 사고 대응 과정을 함께 최종 평가하겠습니다.

평가위원은 사고가 있었다는 사실을 없던 일로 하지 않는다. 대신 도윤이 문제를 숨기지 않고 정상 원본, 확인 시각, 변경 경로를 근거로 설명한 대응과 개선안의 타당성을 함께 평가한다.

## 발표 이후 후일담

발표 종료 직후 결과 화면으로 건너뛰지 않는다. 평가위원이 퇴장한 발표실의 정적부터 시작해 다음 사건을 순서대로 회수한다.

- 도윤이 발표 리모컨을 내려놓고 긴장을 푸는 장면
- 하린이 검증 등급에 따라 도윤의 직접 대응 또는 끝까지 이어 간 태도를 인정하는 장면
- 태식이 재실행 권한 회수, 감사 로그 첨부, 사고 보고서 작성을 지시하는 장면
- 민재가 재실행 요청과 이상 징후 미보고를 인정하고 공식적으로 사과하는 장면
- 하린이 직접 수치 조작은 확인되지 않았다는 사실과 확인된 책임을 구분해 기록하는 장면
- 복도에서 하린이 과거처럼 책임을 혼자 감당하지 않게 된 변화를 말하는 장면
- 게임사업실로 돌아와 감사 로그, 정상 원본, 복구 기록을 하나의 사고 보고서로 정리하는 장면
- 오후 동안 후속 조치를 완료하고 정직원 전환 결과를 기다리는 장면
- 태식이 검증·복구·보고 태도를 근거로 최종 평가를 설명하는 장면

발표실과 게임사업실은 기존 승인 배경을 재사용하며, 발표실 밖 복도는 전용 배경 `background.presentation_hallway.day`(승인됨)를 사용한다. 감사 종료 장면은 새 이미지를 만들지 않고 게임사업실 배경(`background.office.day`)을 재사용한다. 후일담에는 새로운 선택지를 추가하지 않으며, 기존 오류 검증 등급·신뢰도·호감도에 따라 일부 대사만 달라진다.

## DAY 5 통합 엔딩

업무 엔딩과 관계 엔딩을 따로 출력하지 않는다. 먼저 정직원 전환 여부를 판정하고, 정직원 전환에 성공한 경우에만 하린과의 관계 조건을 확인한다.

```text
업무 판정
→ 오류 검증 등급
→ 근거 자료 복구 결과
→ 최종 신뢰도

정직원 전환 성공 시에만
→ 최종 호감도 확인
→ MIDDLE 또는 HAPPY 결정
```

오류 검증의 다섯 정답 기록과 네 단계 복구 기록은 저장 데이터에 그대로 유지한다. 오류 검증 정답은 검증 등급을 만들고, 복구의 네 선택은 완전 복구 여부를 판정한다. 업무력 수치는 대사와 결과 요약에 반영되지만 엔딩을 직접 나누는 조건은 아니다.

### BAD ENDING · 끝나는 계약

다음 중 하나를 충족하면 진입한다.

- 오류 검증에서 생명 5개를 모두 소진해 직접 검증 실패
- 원본을 고정하지 않고 자동 연결을 유지함
- 최종 신뢰도가 `0 미만`

정직원 전환은 끝내 승인되지 않는다. 이는 "보류되어 다음 기회를 기다리는" 결말이 아니라, DAY 2부터 언급된 계약 기간이 그대로 끝나는 결말이다. 도윤은 빈 사무실에 홀로 남아 책상 짐을 상자에 담으며 무엇이 어긋났는지 되짚는다(실패 사유에 따라 대사가 갈린다: 직접 검증 실패, 복구 마지막 단계 실수, 신뢰도 부족). 하린에게서 `그동안 고생 많았어요. 이건 도윤 씨 잘못이 아니에요.`라는 메시지가 오지만, 그녀가 직접 사무실로 돌아오지는 않으며 엘리베이터 장면과 주말 약속 질문도 나오지 않는다. 마지막 장면에서 도윤은 짐 상자를 들고 사무실을 나선다.

BAD에서는 정직원 전환이 되지 않으므로 하린과의 관계 진전도 발생하지 않는다.

### MIDDLE ENDING · 믿고 일할 수 있는 동료

BAD 조건에 해당하지 않고 HAPPY 조건도 충족하지 않으면 진입한다. 부분 검증이어도 생명을 남기고 근거 자료를 직접 복구하며 신뢰를 유지했다면 정직원 전환은 가능하다. 검증 실패는 담당자 지원으로 자료가 복구되더라도 MIDDLE에 진입하지 않는다.

남은 기술 조사는 보안 담당 부서로 이관되며 도윤의 실패로 처리하지 않는다. 평가위원은 사고를 숨기지 않고 검증 가능한 사실부터 복구한 대응을 인정하고 **정직원 전환을 승인**한다.

퇴근 엘리베이터에서 두 사람은 연애 관계가 아니라 서로 믿고 일할 수 있는 동료로 한 단계 가까워진다.

- **서하린**
  - 앞으로도 잘 부탁해요, 한도윤 씨.
- **한도윤**
  - 저도 잘 부탁드립니다, 서하린 선배.
- **서하린**
  - 이제 계속 선배라고 부를 필요는 없을지도 모르겠네요.
- **한도윤**
  - 그러면 뭐라고 불러야 합니까?
- **서하린**
  - 그건 다음에 생각해 봐요.

화면 표기:

```text
MIDDLE ENDING
사수와 신입으로 시작한 두 사람은
서로 믿고 일할 수 있는 동료가 되었다.
```

### HAPPY ENDING · 다음 일정

다음 조건을 모두 충족하면 진입한다.

- 오류 검증에서 생명을 모두 잃지 않고 직접 검증 완료
- 자동 갱신 중지, 현재 분석 원본 `18.4%`, 올바른 분석 기준, 고정 원본 연결을 모두 선택해 근거 자료 완전 복구
- 최종 신뢰도 `8 이상`
- 최종 호감도 `7 이상`

(과거 `NICE ENDING` 명칭. 기존 신뢰도·호감도 `5 이상` 기준이 너무 쉽게 충족돼 HAPPY로 지나치게 자주 진입하는 문제가 있어 상향 조정했다.)

정직원 전환이 승인되고 사건 경위와 재발 방지 조치까지 공식 기록된다. 마지막 장면은 퇴근 엘리베이터 안의 도윤과 하린 두 사람만 보여 준다.

- **서하린**
  - 도윤 씨.
- **한도윤**
  - 네.
- **서하린**
  - 이번 주말에…

짧은 정적 뒤 하린이 도윤을 바라본다.

- **서하린**
  - 시간 괜찮아요?

1층 도착음이 울리고 도윤이 대답하려는 순간 화면을 암전한다. 도윤의 답은 보여 주지 않는다.

화면 표기:

```text
HAPPY ENDING
발표는 끝났지만,
두 사람의 다음 일정은 이제 시작된다.
```

## 추리 판정 원칙

- 기존 단서 탭과 마인드맵을 오류 검증에서도 그대로 사용한다.
- 검증에 도움이 되는 단서가 있는 DAY 탭에만 `근거 있음` 배지를 표시한다.
- 좋은 추리는 사람을 빨리 지목하는 것이 아니라 정상 사실을 먼저 증명하고, 기록으로 인과를 좁히는 방식이다.
- `하린이 아니다`, `민재다`만 고르는 것으로 완전 해결 처리하지 않는다.
- 등록 담당자, 요청 계정, 실행 기능, 연결 대상의 역할을 구분해야 한다.
- 오류 검증 다섯 단계는 실수 기회 5회를 공유하며 다섯 번째 실수에서 즉시 실패 결과창으로 전환된다.
- 오류 검증에서 잘못된 단서를 제시할 때마다 생명과 신뢰도가 각각 1씩 감소한다.
- 검증 실패여도 시스템 담당자가 남은 경로를 확인하므로 DAY 5 스토리는 중단되지 않는다.
- 다섯 단계 오류 검증과 네 단계 원본 복구를 하나의 미니게임으로 이어서 진행한다.
- 오류 검증을 마친 뒤에는 중간 결과창 없이 책임 확인과 원본 복구로 이어지며, 복구가 끝난 뒤 통합 결과창을 한 번만 확인한다.
- 복구 단계에서도 같은 생명과 신뢰도 규칙을 사용하고, 올바른 복구 단계마다 성공 효과음과 화면 피드백을 출력한다.
- 생명을 모두 잃는 즉시 플레이어 조작과 남은 복구 선택을 종료한다.
- 이후 시스템 담당자가 보안 감사 원문 확인, 자동 갱신 중지, 정상 원본 `18.4%` 선택, 분석 기준 확인, 원본 연결 고정을 수행하는 `지원 복구 과정`을 자동 연출로 보여 준다.
- 지원 복구가 끝나도 플레이어의 직접 검증 등급은 `실패`로 유지하며 통합 결과창은 `지원 복구`로 표시한다.
- 검증 실패는 지원 복구 성공 여부와 관계없이 정직원 전환 무산·계약 종료인 BAD 판정으로 이어진다.
- 정직원 전환에 실패한 상태에서는 호감도가 높아도 관계 진전 장면을 출력하지 않는다.
- 호감도 조건 선택지는 숨기지 않는다. 모든 항목을 노출하고, 조건 미달 항목에는 잠금 아이콘·필요 호감도·현재 호감도를 표시하며 모든 입력 방식에서 실행을 막는다.
